How it works

A short explanation of the backup architecture and security boundaries.

1. Select eligible local sources

The owner reviews which files or folders to include. The backup workflow is not designed to automatically capture every file on the computer. Restricted data, downloaded third-party publications, and secrets are excluded unless their use is separately permitted and intentionally configured.

2. Encrypt with restic

restic prepares encrypted, deduplicated repository data on the originating computer. Separate repositories and recovery credentials can be maintained for distinct devices. A restic password is needed to decrypt backup content.

3. Transfer with rclone

rclone connects to the owner's Google Drive account using OAuth 2.0. The application requests the https://www.googleapis.com/auth/drive.file permission rather than unrestricted full-Drive access. The workflow may also query quota and relevant metadata to validate the target account and repository.

4. Verify and restore

The owner can run repository consistency checks and restore snapshots to isolated destinations. A successful upload alone is not treated as proof that files can be restored. Restore verification and periodic authorization renewal may be required.

5. Control access and retention

OAuth tokens and restic recovery credentials are stored in restricted, device-local locations. Google Drive stores the encrypted backup objects, while the owner controls backup source policies and deletion. Revoking OAuth does not automatically remove data already stored in Drive.

Privacy: This documentation does not provide access to stored backups or reveal local credentials. Read the Privacy Policy for data use, retention, and contact information.

Project description updated October 12, 2026. Features described are for a private, owner-operated workflow; deployment and backup coverage depend on its explicitly approved configuration.
